## 一、现状盘点

项目**已有用户系统的骨架，但没有闭环**。具体：

### 已有（可复用）

| 组件 | 位置 | 说明 |
|---|---|---|

| JWT 认证 | `app/core/auth.py` | HS256 令牌，Cookie（`ip_landmark_access_token`）+ Bearer 双通道，`get_current_member` 依赖注入，开发环境 `dev_bypass_auth` 自动以 dev 用户（PREMIUM）通过 |

| 特性矩阵 | `app/services/entitlements.py` | `EntitlementService`（text_catalog/exports/static_map/static_route/personalized_itinerary），**当前三层全 True，形同虚设** |
| 管理员守卫 | `app/api/admin.py:19` | `require_admin` = 校验静态 `X-Admin-Token` 头（`settings.admin_api_token`），**与用户身份无关** |
| 贡献归属 | `app/models/contribution.py` | `LandmarkContribution.contributor_user_id` → User（自动提权的数据基础已具备） |
| 行程功能 | `app/api/itineraries.py` | 个性化行程端点已挂 `require_entitlement("personalized_itinerary")`；官方路线管理在 `/api/v1/admin/routes`（X-Admin-Token 守卫） |
| 相册/一键入库 | `app/api/album.py`、`app/api/agent.py` | 已挂 `require_member` |

### 缺失（本计划要补）

1. **注册 / 登录 / 登出接口与页面** —— 完全没有；`password_hash` 从未真正哈希过（只有 dev/anonymous 占位串）
2. **基于账号的管理员** —— 现在 `require_admin` 只认静态令牌，与登录用户无关
3. **用户角色层级** —— 只有付费 tier（FREE/LITE/PREMIUM），没有"权限角色"概念
4. **用户管理** —— 无列表/改角色/封禁/删除
5. **条目管理** —— 无条目修改、下架（takedown）接口（publish 有，反向没有）
6. **封禁机制** —— 无
7. **自动提权** —— 无"贡献被采纳 → 升级"联动

## 二、目标权限模型

### 2.1 两个维度，不得混用

你定义的三级（管理员/一级/二级）是**权限角色**；现有 FREE/LITE/PREMIUM 是**付费会员层**。
二者语义不同（一个是"能做什么"，一个是"付了多少钱"），按 anti-entropy 原则拆为两个独立字段，互不影响：

- `User.role`：`admin / level1 / level2`（权限角色，本计划新增）
- `Membership.tier`：FREE/LITE/PREMIUM（付费会员，**保留现状不动**，未来商业化时再差异化）

### 2.2 角色定义

| 角色 | 值 | 获得方式 | 权限 |
|---|---|---|---|
| 管理员 | `admin` | 初始种子 / 其他管理员提权 | 全部功能：审核、条目管理（删除/修改/下架）、用户管理（角色/封禁/删除） |
| 一级普通用户 | `level1` | 注册默认二级 → **贡献条目被管理员发布后自动升级** | 生成个性化行程 + 二级全部权限 |
| 二级普通用户 | `level2` | 注册默认 | 浏览地标条目、一键入库、API 配置、相册管理 |

### 2.3 权限矩阵（唯一事实源）

| 功能 | 未登录 | 二级 | 一级 | 管理员 |
|---|---|---|---|---|
| 浏览目录 / 详情 / 相册 / 官方路线 | ✓ | ✓ | ✓ | ✓ |
| 一键入库（AI Agent） | ✗ | ✓ | ✓ | ✓ |
| 相册管理（上传 / AI 找图 / 提交） | ✗ | ✓ | ✓ | ✓ |
| 个人密钥管理（自配 DeepSeek/高德/博查/美团） | ✗ | ✓ | ✓ | ✓ |
| API 配置（系统级密钥） | ✗ | ✗ | ✗ | ✓ |
| 生成个性化行程 | ✗ | ✗ | ✓ | ✓ |
| 审核地标（review / publish） | ✗ | ✗ | ✗ | ✓ |
| 条目管理（修改 / 下架 / 删除） | ✗ | ✗ | ✗ | ✓ |
| 用户管理（角色 / 封禁 / 删除） | ✗ | ✗ | ✗ | ✓ |

实现上以 `app/services/permissions.py` 的角色矩阵为唯一事实源；
`EntitlementService` 改为按 role + tier 双查（tier 特性维持现状，留待商业化）。

### 2.4 密钥隔离架构（已定案：按用户隔离）

**原则：系统级密钥只给管理员使用；普通用户要用相应功能，必须自配密钥。**

- 功能调用密钥的解析顺序（`KeyResolutionService.resolve(db, member, provider)`）：
  1. 未登录 → 直接拒绝（401）
  2. 用户自配的启用密钥 → 使用之
  3. 用户是管理员且未自配 → 回落系统级密钥（`.env`）
  4. 其余 → 403 `{"code": "user_key_required", "provider": ..., "config_url": "/account/api-keys"}`，前端引导去个人密钥页
- **不存在"普通用户回落系统密钥"的路径**；未自配密钥时相应功能不可用（而非降级用系统 Key）
- 免密钥功能不受影响：浏览、地图瓦片（OSM）、AI 找图（Wikimedia Commons）
- 各功能所需 provider 清单：

| 功能 | 必需 Key | 可选增强 |
|---|---|---|
| 一键入库（AI Agent） | `deepseek` | `bocha`（缺省时跳过联网核实并提示） |
| AI 找图（Commons） | 无 | `deepseek`（检索词生成与排序；未配置则直接用地标名检索） |
| 个性化行程（一级） | `amap` | `meituan`（M4 实施时按 ItineraryService 实际调用核定必选清单） |
| 地理编码 / 路线规划 | `amap` | — |

- 系统级密钥继续存 `.env`（现有 `/settings/api` 页与 `/api/v1/api-config/*` 收紧为**仅管理员**）
- 安全：用户密钥静态加密存储（Fernet/AES，密钥由 `APP_SECRET_KEY` HKDF 派生），接口永不回传明文，只回掩码提示（`sk-7****a5af`）
- 保存前做"连通性验证"（复用现有 verify 探针），通过才落库，记录 verified_at

## 三、数据模型变更

```python
# app/models/enums.py
class UserRole(StrEnum):
    ADMIN = "admin"
    LEVEL1 = "level1"
    LEVEL2 = "level2"

class UserStatus(StrEnum):
    ACTIVE = "active"
    BANNED = "banned"

# app/models/user.py 新增字段
role: Mapped[str] = mapped_column(default=UserRole.LEVEL2.value, nullable=False, index=True)
status: Mapped[str] = mapped_column(default=UserStatus.ACTIVE.value, nullable=False)
last_login_at: Mapped[datetime | None]
```

**新增用户密钥表**（`app/models/user_api_key.py`）：

```python
class UserApiKey(TimestampMixin, Base):
    __tablename__ = "user_api_keys"

    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id", ondelete="CASCADE"), index=True)
    provider: Mapped[str] = mapped_column(String(32))  # deepseek / amap / bocha / meituan
    encrypted_value: Mapped[str] = mapped_column(String(512))  # Fernet 加密后的密钥
    key_hint: Mapped[str] = mapped_column(String(32))  # 掩码展示，如 sk-7****a5af
    is_active: Mapped[bool] = mapped_column(default=True)
    verified_at: Mapped[datetime | None]
    # 唯一约束 (user_id, provider)；重复保存即覆盖
```

**存量迁移规则**（一次性脚本 `scripts/migrate_user_roles.py`）：

- `is_admin=True` → `role=admin`；其余用户 → `role=level2`
- `is_admin` 字段保留一个过渡版本（只读兼容），下个版本删除

**种子数据**：`dev@iplandmarks.local`（开发 bypass 用户）→ `role=admin`。

## 四、后端 API 变更

### 4.1 认证闭环（新增 `app/api/auth.py` + `app/web/auth.py`）

| 端点 | 说明 |
|---|---|
| `POST /api/v1/auth/register` | email + password（≥8 位），PBKDF2-SHA256 + 随机盐（`hashlib.pbkdf2_hmac`，免新增依赖）；注册即 level2；email 唯一 |
| `POST /api/v1/auth/login` | 校验后签发 JWT，写 HttpOnly+SameSite=Lax Cookie；更新 `last_login_at`；**banned 用户拒绝登录** |
| `POST /api/v1/auth/logout` | 清 Cookie |
| `GET /api/v1/auth/me` | 返回 user_id、email、role、tier、权限摘要 |
| 页面 | `GET /login`、`GET /register`（表单页，提交走 API） |

### 4.2 权限依赖重构（`app/core/auth.py`）

- `require_admin` **从 admin.py 移入 core/auth.py**，改为：登录用户 `role=admin`；
  过渡期同时接受 `X-Admin-Token`（现有脚本/测试兼容），标注弃用时间表
- 新增 `require_role(minimum)`：按 `level2 < level1 < admin` 序比较；403 返回 `{"code": "role_required", "required": ...}`
- `get_current_member` 增加 `status=banned` 校验 → 403（封禁即时生效，含已签发 token）
- `CurrentMember` 增加 `role` 字段

### 4.3 现有端点挂守卫

| 端点 | 现状 | 调整为 |
|---|---|---|
`POST /api/v1/agent/landmarks/intake`（一键入库） | require_member | 不变（即二级+） |
| 相册编辑器 5 个端点 | require_member | 不变 |
| `/api/v1/api-config/*`（系统密钥） | require_member | **收紧为 require_admin**；变更记审计 |
| `POST /api/v1/itineraries`、`/finalize`、`/reprocess-meituan` | require_entitlement | `require_role("level1")`（叠加 tier 特性） |
| `/api/v1/admin/*`（review/publish/imports/data-quality/discover/routes） | X-Admin-Token | role=admin（过渡期双轨） |
| **新增** `PATCH /api/v1/admin/landmarks/{id}` | — | 条目修改（管理员） |
| **新增** `POST /api/v1/admin/landmarks/{id}/unpublish` | — | 下架：published_at 置空，回候选 |
| **新增** `DELETE /api/v1/admin/landmarks/{id}` | — | 删除（软删，保留审计） |

### 4.4 用户管理（管理员）

| 端点 | 说明 |
|---|---|
| `GET /api/v1/admin/users?query=&role=&status=` | 分页列表 |
| `PATCH /api/v1/admin/users/{id}` | 改角色（不得降级/封禁自己） / 封禁 / 解封 |
| `DELETE /api/v1/admin/users/{id}` | 删除（软删；其贡献置匿名归属） |

### 4.5 用户密钥管理与解析链（新增 `app/api/user_keys.py` + `app/services/key_resolution.py`）

| 端点 | 说明 |
|---|---|
| `GET /api/v1/me/api-keys` | 本人密钥列表：provider、key_hint、is_active、verified_at（**永不返回明文**） |
| `PUT /api/v1/me/api-keys/{provider}` | 设置/覆盖（先做格式与连通性验证，通过才落库） |
| `DELETE /api/v1/me/api-keys/{provider}` | 删除 |
| `POST /api/v1/me/api-keys/{provider}/verify` | 手动触发连通性验证 |

- provider 白名单：deepseek / amap / bocha / meituan（与系统配置一致）
- `KeyResolutionService.resolve()` 挂入各集成客户端：`_ensure_llm`、AMap、博查、美团客户端在**请求上下文**中优先取用户密钥（改造点：这些客户端当前在服务构造时单例化，需改为按请求解析或传入解析结果）
- 403 错误体带 `config_url`，前端统一引导至个人密钥页

### 4.6 自动提权（二级 → 一级）

挂接点：`ReviewService.publish()` 成功后（发布即"管理员通过上架"）：

```python
contribution = ...  # 该地标的 LandmarkContribution
if contribution and contribution.contributor_user_id:
    user = db.get(User, contribution.contributor_user_id)
    if user and user.role == UserRole.LEVEL2.value:   # 幂等：admin/level1 不动
        user.role = UserRole.LEVEL1.value
```

规则：**只升不降**；多条贡献被发布只升一次；`unpublish` 不回收等级。

## 六、测试计划

- **认证**：注册（重复 email/弱密码）、登录（错误密码/banned 拒绝）、登出、me；Cookie 与 Bearer 双通道
- **权限矩阵（参数化）**：关键端点 × 4 种身份（匿名/二级/一级/管理员）逐格断言
- **封禁即时性**：登录 → 封禁 → 原 token 请求被拒
- **自动提权**：二级用户贡献 → review → publish → role=level1；重复发布幂等；管理员贡献不降级
- **用户管理**：改角色/封禁/删除；不能操作自己；被删用户贡献归属置空
- **密钥隔离**：普通用户未配 Key → 403 user_key_required；配 Key 后功能放行且**不触碰系统 Key**；管理员回落系统 Key；密钥接口永不回明文；加密落库；验证失败不落库
- **迁移**：is_admin → admin；普通用户 → level2
- **回归**：现有 236 个测试全绿（admin 测试改用管理员登录态或保留 X-Admin-Token 双轨）

## 七、里程碑

| 阶段 | 内容 | 验收标准 | 预估 |
|---|---|---|---|
| **M1 认证闭环** | 注册/登录/登出/me + 密码哈希 + 登录注册页 + Header 状态区 | 可注册、登录、退出；`require_member` 由真实登录满足 | 0.5~1 天 |
| **M2 角色与矩阵** | role/status 字段 + 迁移脚本 + `require_role`/`require_admin` 重构 + 矩阵落地 + 行程端点挂 L1 | 参数化矩阵测试全绿；dev 用户为 admin | 1 天 |
| **M3 自动提权** | publish 联动升级 | 发布候选后贡献者自动升一级，幂等 | 0.5 天 |
| **M4 密钥隔离** | UserApiKey 模型 + 加密存储 + KeyResolutionService 解析链 + /me/api-keys API + 个人密钥页 + 系统密钥页收紧 admin + 集成客户端按请求解析改造 | 普通用户未自配 Key 无法用相应功能；管理员可用系统 Key；矩阵测试绿 | 1.5 天 |
| **M5 管理能力** | 用户管理 API + /admin/users 页 + 条目修改/下架/删除 | 管理员可全流程管理用户与条目 | 1 天 |
| **M6 收尾** | 登录限速（内存级失败计数）、README、文档、全量回归 | 全量测试绿；文档齐 | 0.5 天 |

**总计约 4.5~5 个工作日**。M1+M2 完成后即具备最小可用权限体系；M4 密钥隔离是本计划的安全核心，必须在 M5 前完成。

## 八、兼容与迁移注意

1. **conftest/工厂**：`tests/factories.py` 的 `create_member` 增加 role 参数（默认 level2）；新增 `create_admin`
2. **X-Admin-Token 双轨**：现有管理员测试与外部脚本不断链，M5 后评估下线
3. **dev bypass**：仅非生产生效（现状保持），dev 用户 role=admin，避免开发环境权限误判
4. **匿名共享身份**（anonymous@iplandmarks.local）：role=level2、不可登录（password_hash 为占位）——仅用于行程归属，不参与权限判定
5. **既有 236 测试**：admin 类测试在 M2 同步适配；require_member 类（相册/入库）无需改动；api-config 测试在 M4 收紧后需补管理员身份
6. **`.env` 密钥的定位变化**：M4 后 `.env` 中的 MEITUAN/AMAP/DEEPSEEK/BOCHA 仅作为**系统级密钥（管理员回落用）**，不再对普通用户生效；README 与 API 配置页文案同步说明
