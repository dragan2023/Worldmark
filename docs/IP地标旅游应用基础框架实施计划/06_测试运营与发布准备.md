# 06 — 测试、运营与发布准备

## 1. 摘要

- 优先级：P0（最终门禁）
- 预计工作量：3–5 人日
- 直接依赖：04、05；测试工作自 01 起持续进行
- 阶段目标：将基础框架验证为可演示、可维护、数据可追溯且不误导用户的 MVP，形成上线前检查清单与部署说明。

## 2. 前置阅读

1. `docs/IP地标旅游应用基础框架实施计划/00_计划索引.md` 全文。
2. 01–05 各阶段的验收标准、禁止事项和测试目录。
3. `README.md`、`.env.example`、`requirements.txt`、`alembic.ini` 与全部 `tests/`。

## 3. 任务详情

### 3.1 完成分层测试与质量门禁

补齐模型、服务、API、浏览器冒烟测试；测试数据库与开发数据库分离。为公开目录、导出、会员地图、个性化行程建立一条端到端关键路径：导入审核数据 → 发布 → 筛选 → 免费导出 → 会员访问地图/路线 → 高级会员生成并编辑计划。

新增 `scripts/verify_mvp.ps1`，依次运行迁移、数据质量检查、格式/静态检查和 pytest；脚本失败应返回非零状态。将确定性模拟行程生成器作为 CI 默认实现，真实 LLM 调用只在显式配置的集成环境执行。

### 3.2 完成数据与内容发布检查

新增 `docs/上线前数据检查清单.md`。上线前逐项确认每个已发布地标都有来源、审核记录、原创摘要、地理层级、更新日期、交通免责声明；每条公开线路的站点均可访问；所有公开页面显示来源与最后更新日期。抽查三类模块各 3 条记录，复核作品关联、地址、坐标和交通文字。

数据质量脚本输出为零阻断项才允许发布。对过期、失效、版权存疑或地点变更记录撤回发布，保留后台审核历史。

### 3.3 完成安全、隐私和运行文档

更新 `README.md`，写明安装、环境变量、数据库迁移、导入、审核、测试和本地启动步骤。新增 `docs/隐私与数据保留说明.md`、`docs/运行手册.md`、`docs/故障处理手册.md`，覆盖账号数据删除、日志脱敏、密钥轮换、AI 服务超时、地图供应商故障、导出错误和数据库备份恢复演练。

生产配置至少启用 HTTPS 反向代理、可信主机/CORS 限制、带过期时间的令牌、密码哈希、管理员路由鉴权、错误日志脱敏和数据库定期备份。订单、收款、第三方登录与实时导航均不在本次发布范围。

### 3.4 进行 MVP 可用性验证与上线判定

依照用户原始思考，访谈 10–20 名目标用户（文学、游戏、影视爱好者至少各 3 名）并观察三项任务：按作品找地点、按城市筛选并导出、理解不同会员权益。记录完成率、困惑点和愿意为地图/行程能力付费的反馈。

这里的“MVP 验证”是产品方向验证：确认目标用户能否完成核心任务、是否理解并愿意使用地图/行程权益，以及哪类内容最值得优先扩展；它不是“代码是否能运行”的技术测试。上线判定不以访谈人数替代质量门禁：所有自动化测试、数据检查和权限检查必须先通过。把访谈中的改进项写入 `docs/MVP验证记录.md`，按影响/证据/建议排序；本计划只验证用户对不同功能层级的使用意愿，不涉及任何收款行为。

## 4. 精确文件范围

1. 新增或更新：`scripts/verify_mvp.ps1`、`tests/e2e/test_mvp_journey.py`、所有阶段缺失的 `tests/**`。
2. 新增：`docs/上线前数据检查清单.md`、`docs/隐私与数据保留说明.md`、`docs/运行手册.md`、`docs/故障处理手册.md`、`docs/MVP验证记录.md`。
3. 更新：`README.md`、`.env.example`、`requirements.txt`（仅保留实际使用依赖）。

## 5. 禁止修改与风险红线

1. 不以“页面能打开”替代权限、数据、导出和生成结果验证。
2. 不使用生产账号、真实用户自由文本或真实 API 密钥跑自动化测试。
3. 不在缺少来源、审核或免责声明的情况下发布任一地标或线路。
4. 不把用户访谈反馈描述成代表性市场结论；它只用于 MVP 决策。

## 6. 验收标准

- [ ] `scripts/verify_mvp.ps1` 在干净测试环境执行迁移、质量检查和测试全部成功。
- [ ] 关键端到端路径覆盖三类 IP、三档权益和两种导出格式。
- [ ] 已发布数据零阻断问题；抽查记录的地址、来源、作品关联与交通文案一致。
- [ ] 运行、隐私、故障、备份恢复和数据撤回文档可供新维护者执行。
- [ ] 10–20 名目标用户的任务验证已记录，且不会绕过质量门禁或无资质收款。
