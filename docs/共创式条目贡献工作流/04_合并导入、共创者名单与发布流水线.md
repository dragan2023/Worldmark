# 04 — 合并导入、共创者名单与发布流水线

## 1. 摘要

- 优先级：P1（让通过审核的条目真正进入应用，并建立共创者名单）
- 预计工作量：3–4 人日
- 直接依赖：01；03 的机器人确保合入的条目已通过校验
- 阶段目标：维护者合入共创 PR 后，自动（或一键）把条目并入种子数据，以 PR 作者的 GitHub 用户名落署名；维护共创者名单文件 `data/contributions/contributors.json`，并在项目前端新增 `/contributors` 独立页面按请求实时读取该文件展示。

## 2. 前置阅读

1. `app/scripts/seed_initial_landmarks.py`（种子导入与发布流程）。
2. `app/services/import_landmarks.py`（`import_csv` 与判重逻辑）。
3. `app/models/contribution.py`（`LandmarkContribution` 署名表）。
4. `data/seed/landmarks_verified.csv`、`data/seed/landmark_content.json`（种子数据格式）。
5. `app/main.py`、`app/web/contributions.py`、`app/templates/_header.html`、`app/templates/contributions/new.html`（Web 路由注册、模板与导航接入方式）。
6. 03 阶段 `.github/workflows/review-contribution.yml`（合入入口）。

## 3. 任务详情

### 3.1 导入脚本 `scripts/import_contribution_entries.py`

遍历 `data/contributions/entries/**/*.csv`，对每个文件：

1. 再次用 01 校验脚本验证（防绕过）。
2. 追加到 `data/seed/landmarks_verified.csv`（按 `ip_type + work_title + landmark_name + normalized_address` 归一化判重，重复跳过并记录日志）。
3. 三段式简介合并进 `data/seed/landmark_content.json`（按 `ip_type + work_title + landmark_name` 匹配，新地标追加）。
4. 处理完成后把原文件移动到 `data/contributions/entries/archive/YYYY-MM-DD/`，并生成处理日志。

脚本必须幂等：重复执行不产生重复行、不重复归档。脚本接收 `--contributor <github_username>` 参数（由发布工作流传入 PR 作者用户名），用于更新共创者名单。

### 3.2 共创者名单文件 `data/contributions/contributors.json`

1. 结构：按 GitHub 用户名去重的数组/映射，每个成员包含 `username`、`github_url`（`https://github.com/<username>`）、`first_merged_at`（ISO 8601 日期）、`merged_entries`（累计合并条目数）。
2. 维护方式：发布工作流在导入成功后把 PR 作者用户名 upsert 进该文件；仅流水线与维护者写入，共创 PR 不得修改（由 03 路径闸门与 CODEOWNERS 双重保护）。
3. 页面与 API 按请求实时读取该文件，不缓存，保证「同步显示」。

### 3.3 前端共创者名单页面 `/contributors`

1. 新增 `app/web/contributors.py`：路由 `GET /contributors` 读取 `data/contributions/contributors.json`，渲染 `app/templates/contributors/index.html`（展示用户名、GitHub 链接、加入时间、累计条目数；空名单时显示引导文案指向提示词包）。
2. 新增公开 API `GET /api/v1/contributors`（`app/api/contributors.py`），返回名单 JSON，供页面与外部使用。
3. 在 `app/templates/_header.html` 主导航增加「共创者」链接指向 `/contributors`；在 `app/main.py` 注册新路由。
4. 测试：`tests/web/test_contributors.py`（页面 200、名单渲染、空名单）、`tests/api/test_contributors.py`（JSON 结构与既有数据一致）。

### 3.4 署名落库

扩展 `app/scripts/seed_initial_landmarks.py`：导入种子 CSV 时按「作品+地标名」匹配共创者名单，为有对应 GitHub 用户名的记录创建 `LandmarkContribution(contributor_name=<github_username>)`；无匹配时保持原行为（不创建）。`landmark_contributions` 表已存在，无需新增 Alembic 迁移，仅扩展读取逻辑并保持向后兼容。

### 3.5 发布工作流 `.github/workflows/publish-contributions.yml`

1. 触发：push 到 `main` 且路径含 `data/contributions/entries/**`。
2. 步骤：checkout → `actions/setup-python`（3.13）→ `pip install -r requirements.txt` → 用 GitHub API 反查本次推送提交关联的 PR 取作者 `user.login`（手动触发时用 `workflow_dispatch` 输入）→ 运行导入脚本 `--contributor <username>` → 更新 `contributors.json` → 若 `data/seed/`、`contributors.json` 或 `archive/` 有变更，用仓库 Secret `WORLDMARK_ADMIN_TOKEN`（管理员 PAT，配合 `enforce_admins=false` 直推 main）提交回 `main`，仅提交这些路径。

> 回写为什么用管理员 PAT 而非 `GITHUB_TOKEN`：`GITHUB_TOKEN` 永远受分支保护约束，直推 main 会被「两个必检检查」拦截（实测 GH006）；个人仓库（非组织）又不允许把 GitHub Actions 设为 ruleset 的 bypass 角色，无法用 ruleset 放行。因此分支保护采用 `enforce_admins=false`（仅管理员可绕过，用于自动回写），共创者 PR 的两个必检检查仍然强制生效。
> 回写 push 必须清除 `actions/checkout` 注入的 `http.https://github.com/.extraheader`：该请求头携带 `GITHUB_TOKEN`，优先级高于 URL 里的管理员 PAT，实测会导致回写 push 以 `github-actions[bot]` 身份执行、被 GH006/403 拦截（本地直推正常、Actions 内失败即此原因）。正确做法：push 前执行 `git config --unset-all http.https://github.com/.extraheader`，再以 `https://<管理员用户名>:${ADMIN_TOKEN}@github.com/${GITHUB_REPOSITORY}.git` 推送。
> 回写提交不使用 `[skip ci]`：否则会连 Pages 部署工作流一起跳过，导致新共创者加入后名单页面不更新；发布工作流自身因脚本幂等、无新增条目时跳过提交，不会死循环。
3. 数据库发布默认不在 CI 执行：由维护者在部署时运行 `.venv\Scripts\python.exe -m app.scripts.seed_initial_landmarks`（或显式设置 `DEPLOY_DB=1` 时执行），保持「CI 备数据、维护者发布」的稳妥边界。

### 3.6 上线检查清单同步

在 `docs/上线前数据检查清单.md` 增加：entries 目录是否已清空/归档、种子数据去重、共创者名单与署名完整性、`/contributors` 页面可访问、已发布地标可查询等检查项。

## 4. 精确文件范围

1. 新增：`scripts/import_contribution_entries.py`、`tests/scripts/test_import_contribution_entries.py`、`.github/workflows/publish-contributions.yml`。
2. 新增：`data/contributions/contributors.json`（初始空名单）、`app/web/contributors.py`、`app/api/contributors.py`、`app/templates/contributors/index.html`、`tests/web/test_contributors.py`、`tests/api/test_contributors.py`。
3. 修改：`app/main.py`（注册路由）、`app/templates/_header.html`（导航链接）、`app/scripts/seed_initial_landmarks.py`（署名落库，向后兼容）、`docs/上线前数据检查清单.md`。
4. 数据文件：`data/seed/landmarks_verified.csv`、`data/seed/landmark_content.json`、`data/contributions/contributors.json` 由流水线追加，不手工编辑。

## 5. 示例

共创者名单结构：

```json
{
  "contributors": [
    {
      "username": "octocat",
      "github_url": "https://github.com/octocat",
      "first_merged_at": "2026-08-20",
      "merged_entries": 3
    }
  ]
}
```

归档结构：

```text
data/contributions/entries/
├─ README.md
├─ literature/
├─ game/
│  └─ black-myth-wukong--foguang-temple.csv   # 待导入
└─ archive/
   └─ 2026-08-17/
      └─ black-myth-wukong--foguang-temple.csv  # 已导入
```

处理日志示例：`imported black-myth-wukong--foguang-temple.csv -> seed row #42, contributor=octocat`

## 6. 禁止修改与风险红线

1. 导入脚本不修改任何 `app/` 业务逻辑，只读 entries、写 seed/archive/contributors.json。
2. 不自动直连生产数据库；数据库发布始终由维护者显式执行。
3. 回写提交只允许发生在 `data/seed/`、`data/contributions/contributors.json` 与 `data/contributions/entries/` 下，防止机器人越权。
4. 重复/冲突条目在导入阶段再次判重，冲突时记录日志并跳过，不静默覆盖既有已发布数据。
5. 共创者名单只由流水线 upsert，任何人不得手工覆盖既有用户名记录（如确实需要修正，由维护者走 `data/seed/` 同级的受保护修改）。

## 7. 验收标准

- [ ] 构造 1 条合法 entry → 运行导入脚本（带 `--contributor`）→ 种子 CSV 出现该行、content JSON 出现对应简介、`contributors.json` 出现该用户名、原文件移入 archive；再次运行不产生重复。
- [ ] `/contributors` 页面返回 200 并正确渲染名单与 GitHub 链接；`GET /api/v1/contributors` 返回与文件一致的 JSON；空名单显示引导文案。
- [ ] 在临时 SQLite 测试库运行 `seed_initial_landmarks.py` → 新地标可进入 candidate 并经 review/publish 后查询，`landmark_contributions` 含 GitHub 用户名署名。
- [ ] `.venv\Scripts\python.exe -m pytest` 全绿（既有贡献相关测试不回归）。
- [ ] 发布工作流在测试仓库 push 后只提交 `data/seed/`、`contributors.json` 与 `archive/`，不触发自身循环。
