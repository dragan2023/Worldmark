### 3.5 main 分支保护规则（实际配置记录，2026-08-18 生效）✅

实际通过 REST API 写入并验证生效：

- required_status_checks.strict = true（对应「Require branches to be up to date before merging」）
- required_status_checks.contexts = [`validate-contribution`, `文件封锁检查`]（两个都必须通过才能合并）
- enforce_admins = false（管理员可绕过必检检查直推 main，供发布流水线用管理员 PAT 自动回写数据；共创者 PR 的两个必检检查仍然强制生效）
- 未启用：强制 PR 评审（required_pull_request_reviews）、conversation resolution、force push / 删除限制（如需再加）

**检查名必须与 `.github/workflows/review-contribution.yml` 的 job name 完全一致**：

| 工作流 job | 检查名 |
| --- | --- |
| `validate-contribution` | `validate-contribution` |
| `path-gate`（name 为「文件封锁检查」） | `文件封锁检查` |

配置方法 A（GitHub 网页）：Settings → Branches → Add classic branch protection rule → Branch name pattern 填 `main` → 勾选 Require status checks to pass → 在 Search status checks 输入框输入检查名并勾选 → Create。

> ⚠️ 注意：GitHub 只把「在 main 分支上运行过」的检查列为可选。本工作流只监听 `pull_request_target`，检查从不在 main 上运行，因此 UI 列表/搜索框可能为空、加不上；此时用方法 B。

配置方法 B（REST API，可写入任意检查名，推荐）：PUT `/repos/{owner}/{repo}/branches/main/protection`，请求体：

```json
{
  "required_status_checks": { "strict": true, "contexts": ["validate-contribution", "文件封锁检查"] },
  "enforce_admins": false,
  "required_pull_request_reviews": null,
  "restrictions": null
}
```

需要带 `repo` 权限的 token；PUT 会整体覆盖该分支保护规则，执行前先 GET 当前规则确认不会误删其他设置。

验证记录：配置后测试 PR #1 重新跑两个检查并全绿，维护者成功合并（2026-08-18）。

> 2026-08-18 补充：发布流水线回写 main 曾因分支保护被拦截（GH006）。已确认个人仓库无法把 GitHub Actions 设为 ruleset bypass 角色，故放弃 ruleset 迁移，保持经典分支保护并把 `enforce_admins` 改为 `false`：发布流水线改用管理员 PAT（Secret `WORLDMARK_ADMIN_TOKEN`）直推回写，并修复署名 bug（按 PR 作者而非合并人署名）。共创者 PR 的两个必检检查与文件封锁不受影响。
> 2026-08-18 补充（最终根因）：改用管理员 PAT 后回写仍被 GH006 拦截，实测根因是 `actions/checkout` 注入的 `http.https://github.com/.extraheader` 请求头（携带 `GITHUB_TOKEN`）优先级高于 URL 里的管理员 PAT，导致 Actions 内 push 以 `github-actions[bot]` 身份执行。修复：push 前执行 `git config --unset-all http.https://github.com/.extraheader`。修复后完整端到端（PR #2 测试条目 → 机器人检查 → 合并 → 自动导入/归档/回写 → Pages 名单页自动更新）已跑通，测试数据已清理。
