# 01 — 共创条目数据入口与校验能力

## 1. 摘要

- 优先级：P0（后续所有阶段的基础）
- 预计工作量：2–3 人日
- 直接依赖：无（复用既有 `CandidateRow` 与 CSV 模板）
- 阶段目标：定义「一条共创地标 = 一个 CSV 文件」的数据入口，提供无数据库依赖的本地校验脚本，让 Harness 与 GitHub 审核机器人复用同一套校验规则。

## 2. 前置阅读

1. `data/templates/landmark_candidate_template.csv`（22 列模板与表头顺序）。
2. `app/services/import_landmarks.py` 的 `REQUIRED_COLUMNS` 与 `CandidateRow`（字段校验逻辑）。
3. `scripts/validate_contribution_entry.py` 的三段式简介检查（与条目数据入口共用同一规则）。
4. `docs/数据采集规范.md`、`docs/来源分级与审核准则.md`（字段与来源要求）。
5. `data/seed/landmarks_verified.csv`（重复检查基准与表头样例）。

## 3. 任务详情

### 3.1 建立条目目录

新增 `data/contributions/entries/`，含子目录 `literature/`、`game/`、`screen/`（各放一个 `.gitkeep` 保证目录入库）与 `README.md`。README 说明目录契约：只允许新增条目 CSV、命名规则、禁止事项、指向 `docs/数据采集规范.md`；该文件归维护者所有，共创 PR 不得修改。

### 3.2 定义条目文件格式

1. 每一条共创地标 = 一个 UTF-8 CSV 文件，表头与 `data/templates/landmark_candidate_template.csv` 完全一致（既有 22 列，不新增列）；署名不在文件中体现，由 GitHub 用户名在合并时确定（见 04 阶段）。
2. 文件命名：`<work_slug>--<landmark_slug>.csv`，slug 全小写、单词用连字符连接，文件必须位于与 `ip_type` 一致的子目录，例如 `game/black-myth-wukong--foguang-temple.csv`。
3. 每文件只能有一行数据；`latitude`/`longitude` 允许留空；`description` 必须同时包含「在作品中的重要地位：」「主要出现的情节：」「现实地标介绍：」三段前缀；`source_url` 必须是 HTTP/HTTPS URL；`accessed_at` 必须是 ISO 8601 时间。

### 3.3 编写校验脚本 `scripts/validate_contribution_entry.py`

纯函数入口 `validate_entry_file(path, seed_csv_path, entries_dir) -> EntryValidation`，CLI 仅做参数包装，便于 pytest 与 Actions 直接调用。校验项：

1. 文件名与列头检查：命名正则、列头与模板逐列一致、仅一行数据。
2. 字段级校验：调用 `CandidateRow.model_validate`，复用 ip_type、country_code（ISO 3166-1 alpha-2）、URL、必填字段等全部既有规则。
3. 三段式简介检查：与 `app/api/contributions.py` 的规则一致。
4. 重复检查：与 `data/seed/landmarks_verified.csv` 及 `data/contributions/entries/` 既有文件，按 `ip_type + work_title + landmark_name + normalized_address` 归一化比对；命中返回明确的「重复」错误。
5. 可选来源可达性检查（`--check-source`）：对 `source_url` 做单次受限 HEAD 请求（超时、不解析正文），失败仅降级为 warning，不影响 valid 结论，默认关闭。
6. 输出 JSON：`{"file": ..., "valid": bool, "errors": [...], "warnings": [...], "summary": {...}}`，支持 `--file`、`--dir`、`--changed-files`、`--json` 参数；stdout 强制 UTF-8，保证 Windows 管道重定向与 GitHub Actions 直接消费时字节干净。

### 3.4 单元测试 `tests/scripts/test_validate_contribution_entry.py`

覆盖：合法条目通过；缺必填列、非法 ip_type、非法国家码、非 http(s) 来源、缺三段式、重复条目、坏文件名、空行、多行数据均失败并给出可读错误；坐标留空通过；`--json` 输出可解析。

## 4. 精确文件范围

1. 新增：`data/contributions/entries/{literature,game,screen}/.gitkeep`、`data/contributions/entries/README.md`。
2. 新增：`scripts/validate_contribution_entry.py`、`tests/scripts/test_validate_contribution_entry.py`。
3. 如 `CandidateRow` 模块级导入依赖过重（引入 SQLAlchemy 等），可把 `CandidateRow` 与 `REQUIRED_COLUMNS` 原样导出供校验脚本复用，但不得改变其定义与行为。
4. 修改：无（本阶段不触碰既有数据与业务代码）。

## 6. 禁止修改与风险红线

1. 不修改 `data/templates/landmark_candidate_template.csv` 既有 22 列的顺序与含义；条目文件不新增任何列。
2. 不改变 `CandidateRow` 的校验行为。
3. 校验脚本不得连接数据库、不得读取 `.env`、不得抓取网页正文（来源可达性最多受限 HEAD，且默认关闭）。
4. 不把条目目录误并入 `data/seed/`：种子数据是「已审核发布」基准，entries 是「待审核输入」。

## 7. 验收标准

- [ ] 与种子或既有 entry 重复的条目返回明确的「重复」错误。
- [ ] `--json` 输出无日志噪音，可被 GitHub Actions 直接消费。
